# Tunnel-Lab Architecture

Version: 9.10.3

## 1. Purpose

Test which tunneling protocols work between two Ubuntu 24.04 servers
(A and B), especially behind restrictive networks. For each tunnel the
framework configures both sides, verifies the interface, tests payload
in DIRECT (A->B) and REVERSE (B->A) directions, and reports per-side,
per-tunnel results.

## 2. High-level Design

    +------------------+      Control Channel (TCP+JSON)  +------------------+
    |   Server A       | <==============================> |   Server B       |
    |   Controller     |                                  |   Agent          |
    |                  |                                  |                  |
    |  Orchestrator    |                                  |  Executes cmds   |
    |  Tunnel modules  |                                  |                  |
    +--------+---------+                                  +--------+---------+
             |                                                     |
             |                    Actual Tunnel                    |
             +========== GRE / IPIP / VXLAN / WireGuard ===========+
                              (data plane)

- Server A runs the full application (menu.sh / dashboard).
- Server B runs only the lightweight Agent (agents/runner.py).
- SSH is used only to deploy and start the Agent. All further
  communication goes through the Control Channel.

## 4. Core Concepts

### 4.1 TunnelModule

Every tunnel implements the same contract:

    class TunnelModule(ABC):
        id = "gre"
        name = "GRE"
        category = "Kernel"
        description = "..."
        family = "ipv4"
        applicable_stages = ("iface_a", "iface_b", "icmp", "tcp", "udp")

        # lifecycle (optional)
        def setup(self, ctx, orch): ...
        def teardown(self, ctx, orch): ...

        # phase runners (override for non-standard tunnels)
        def run_direct(self, ctx, orch):  return self._default_phase(ctx, orch, reverse=False)
        def run_reverse(self, ctx, orch): return self._default_phase(ctx, orch, reverse=True)

        # standard commands (used by _default_phase)
        def commands_for_a(self, ctx):          return []
        def commands_for_b(self, ctx):          return []
        def reverse_commands_for_a(self, ctx):  return self.commands_for_a(ctx)
        def reverse_commands_for_b(self, ctx):  return self.commands_for_b(ctx)
        def cleanup_commands_a(self, ctx):      return []
        def cleanup_commands_b(self, ctx):      return []

Rules:
- A module NEVER calls core/orchestrator.py internals directly.
- A module only returns shell commands OR uses public helpers
  (orch.local, orch.remote, orch.remote_run, orch.ssh_l, ...).
- Adding a new standard tunnel = 1 file, no changes to core.

### 4.2 applicable_stages

Which stages matter for this tunnel. The orchestrator and formatter
only consider these when deciding PASS/FAIL and rendering the table.

- ipv4 tunnels: ("iface_a","iface_b","icmp","tcp","udp")
- ipv6 tunnels (SIT): same but tests use IPv6
- WireGuard: ("iface_a","iface_b","icmp")
- SSH_TUN: ("iface_a","iface_b","tcp")

Non-applicable stages render as "–" and don't affect PASS/FAIL.

### 4.3 TestContext

    @dataclass
    class TestContext:
        test_id, tunnel_id, server_a_ip, server_b_ip
        tunnel_local_ip, tunnel_remote_ip
        interface_name, dry_run

### 4.4 Channel

core/channel.py provides:
- Channel: low-level TCP socket with length-prefixed JSON.
- ChannelClient: synchronous request/response for Server A.
- A global message bus (logs/bus.jsonl) for the live dashboard.

Every message is a JSON object with a "type" field.

### 4.5 Phases

DIRECT  (A->B): A initiates config, B follows.
REVERSE (B->A): B initiates config, A follows.

Default phase stages: iface_a, iface_b, icmp, tcp, udp.

## 5. Agent Protocol (JSON message types)

A -> B:
    PING                    -> PONG
    RUN {command}           -> RESULT {rc, stdout, stderr}
    RUN_MANY {commands}     -> RESULTS {results:[...]}
    PROBE {ip}              -> PROBE_RESULT {ok, ip}
    RECV_TCP / RECV_UDP     -> RECV_TCP_RESULT / RECV_UDP_RESULT
    SEND_TCP / SEND_UDP     -> SEND_TCP_RESULT / SEND_UDP_RESULT
    RECV_TCP6 / RECV_UDP6   -> same for IPv6
    SEND_TCP6 / SEND_UDP6   -> same for IPv6

Safety:
- RUN goes through is_safe_raw() in agents/commands.py.
- Allowed prefixes: ip, modprobe, sysctl, wg, wg-quick, iptables,
  nft, ping, echo, cat, ls, which, command -v, mkdir, rm, chmod,
  nc, ss, sleep, systemctl, systemd-run, fuser, pkill, setsid,
  nohup, ipsec, openvpn, apt-get, ssh, sshpass, curl, wget, ...
- Anything else -> ERROR {reason: NOT_WHITELISTED}.

Agent safety on timeout:
- Each RUN runs in a new process group (start_new_session=True).
- On timeout, the WHOLE group is killed with SIGKILL.
- This prevents nc / ssh -L from hanging the agent.

## 6. Adding a New Tunnel

1. Standard tunnel (uses default phase):

       from tunnels.base import TunnelModule

       class MyTunnel(TunnelModule):
           id = "mytunnel"
           name = "My Tunnel"
           category = "Kernel"

           def commands_for_a(self, ctx): return [...]
           def commands_for_b(self, ctx): return [...]
           def cleanup_commands_a(self, ctx): return [...]
           def cleanup_commands_b(self, ctx): return [...]

2. Custom tunnel (own test flow):

       class MyTunnel(TunnelModule):
           id = "mytunnel"
           applicable_stages = ("iface_a", "iface_b", "tcp")

           def run_direct(self, ctx, orch):
               stages = {"iface_a": False, "iface_b": False, "tcp": False}
               ...
               return stages

           def run_reverse(self, ctx, orch):
               ...

3. Nothing else. registry.py auto-discovers it.

DO NOT:
- put tunnel-specific logic in core/orchestrator.py
- hard-code IPs or interface names
- edit other tunnels to add a new one

## 7. Failure Types

Reported in result["reason"]:

    DIRECT_ICMP_FAILED / REVERSE_ICMP_FAILED
    DIRECT_TCP_FAILED / REVERSE_TCP_FAILED
    DIRECT_UDP_FAILED / REVERSE_UDP_FAILED
    IFACE_A_DOWN / IFACE_B_DOWN
    REMOTE_ERROR / TIMEOUT / CLEANUP_ERROR / UNKNOWN

## 8. Versioning Policy

MAJOR.MINOR.PATCH

- PATCH: bugfix, docs.
- MINOR: new tunnel module, new feature.
- MAJOR: breaking change to TunnelModule API or protocol.

On EVERY change, update ALL of:
- VERSION
- main.py (VERSION constant)
- install.sh (Installer version)
- CHANGELOG.md
- ARCHITECTURE.md (if structure changed)
- README.md (if user-facing behaviour changed)
