# Tunnel-Lab Architecture

Version: 9.2.0

## 1. Purpose

Tunnel-Lab tests which tunneling protocols work between two Ubuntu 24.04
servers (Server A and Server B) that are behind restrictive networks
(e.g. Iranian servers with filtering).

For each tunnel the framework:
- configures both sides,
- verifies the interface is up,
- tests ICMP, TCP and UDP payload in DIRECT direction (A -> B),
- tears down and repeats in REVERSE direction (B -> A),
- reports per-side, per-tunnel results with human-readable hints.

## 2. High-level Design

    +------------------+        Control Channel        +------------------+
    |   Server A       | <===== TCP + JSON ==========> |   Server B       |
    |   Controller     |                               |   Agent          |
    |                  |                               |                  |
    |  Orchestrator    |                               |  Agent           |
    |  Tunnel modules  |                               |  Executes cmds   |
    +--------+---------+                               +--------+---------+
             |                                                  |
             |                Actual Tunnel                     |
             +================== GRE / IPIP ====================+
                         (data plane, kernel)

- Server A runs the full application (main.py, UI, orchestrator).
- Server B only runs the lightweight Agent (agents/runner.py).
- SSH is used ONLY to deploy and start the Agent on B. After that,
  all communication goes through the Control Channel.

## 4. Core Concepts

### 4.1 TunnelModule

Every tunnel implements the same contract:

    class TunnelModule(ABC):
        id = "gre"
        name = "GRE"
        category = "Kernel"
        description = "..."

        def commands_for_a(self, ctx):    return [...]
        def commands_for_b(self, ctx):    return [...]
        def reverse_commands_for_a(self, ctx): return self.commands_for_a(ctx)
        def reverse_commands_for_b(self, ctx): return self.commands_for_b(ctx)
        def cleanup_commands_a(self, ctx): return [...]
        def cleanup_commands_b(self, ctx): return [...]

Rules:
- Only returns shell command strings. Does NOT execute them.
- No hard-coded IPs; uses ctx.server_a_ip, ctx.server_b_ip,
  ctx.tunnel_local_ip, ctx.tunnel_remote_ip, ctx.interface_name.
- Core (orchestrator) decides WHEN commands run.
- Module decides WHAT commands run.

### 4.2 TestContext

    @dataclass
    class TestContext:
        test_id: str
        tunnel_id: str
        server_a_ip: str
        server_b_ip: str
        tunnel_local_ip: str
        tunnel_remote_ip: str
        interface_name: str
        ...

### 4.3 Channel

core/channel.py provides:
- Channel: low-level TCP socket with length-prefixed JSON.
- ChannelClient: synchronous request/response for Server A.

Every message is a JSON object with a "type" field. The receiver
matches the "expect" type or times out.

### 4.4 Phases

Each tunnel test runs TWO phases:

    DIRECT  (A -> B): A initiates config, B follows
    REVERSE (B -> A): B initiates config, A follows

Each phase checks:
- iface_a: interface on A exists
- iface_b: interface on B exists
- icmp:    ping in that direction
- tcp:     TCP payload + ACK
- udp:     UDP payload + ACK

Tunnel is PASS only if BOTH phases are fully OK.

## 5. Agent Protocol (JSON message types)

A -> B:
    PING                    -> PONG
    RUN {command}           -> RESULT {rc, stdout, stderr}
    RUN_MANY {commands}     -> RESULTS {results:[...]}
    PROBE {ip}              -> PROBE_RESULT {ok, ip}
    RECV_TCP {port}         -> RECV_TCP_RESULT {ok, from, size}
    RECV_UDP {port}         -> RECV_UDP_RESULT {ok, from, size}
    SEND_TCP {host, port}   -> SEND_TCP_RESULT {ok}
    SEND_UDP {host, port}   -> SEND_UDP_RESULT {ok}

Safety:
- Every RUN command must pass is_safe_raw() in agents/commands.py.
- Allowed prefixes: ip, modprobe, sysctl, wg, iptables, ping, echo, cat, ls.
- Anything else -> ERROR {reason: NOT_WHITELISTED}.

## 6. Adding a New Tunnel (step-by-step)

1. Create tunnels/mytunnel.py:

       from tunnels.base import TunnelModule

       class MyTunnel(TunnelModule):
           id = "mytunnel"
           name = "My Tunnel"
           category = "Kernel"
           description = "..."

           def commands_for_a(self, ctx):
               i = ctx.interface_name
               return [f"ip ... local {ctx.server_a_ip} remote {ctx.server_b_ip}"]

           def commands_for_b(self, ctx):
               i = ctx.interface_name
               return [f"ip ... local {ctx.server_b_ip} remote {ctx.server_a_ip}"]

           def cleanup_commands_a(self, ctx):
               return [f"ip link del {ctx.interface_name} 2>/dev/null || true"]

           def cleanup_commands_b(self, ctx):
               return [f"ip link del {ctx.interface_name} 2>/dev/null || true"]

2. Nothing else. registry.py auto-discovers it.
3. Run python3 main.py -> "Select tunnels" -> your tunnel appears.
4. If reverse behaviour differs, override reverse_commands_for_a/b.
5. If dependencies needed, add modprobe / apt-get in commands_for_a.

DO NOT:
- edit core/orchestrator.py to add a tunnel
- put tunnel-specific logic in ui/ or core/
- hard-code IPs or interface names

## 7. Failure Types

Reported in result["reason"] and rendered by core/advisor.py:

    DIRECT_ICMP_FAILED
    DIRECT_TCP_FAILED
    DIRECT_UDP_FAILED
    REVERSE_ICMP_FAILED
    REVERSE_TCP_FAILED
    REVERSE_UDP_FAILED
    IFACE_A_DOWN
    IFACE_B_DOWN
    REMOTE_ERROR
    TIMEOUT
    CLEANUP_ERROR
    UNKNOWN

## 8. Versioning Policy

MAJOR.MINOR.PATCH

- PATCH: bugfix, install script, docs.
- MINOR: new tunnel module, new feature.
- MAJOR: breaking change in TunnelModule API or protocol.

On EVERY change, update ALL of:
- VERSION
- main.py (VERSION constant)
- CHANGELOG.md
- ARCHITECTURE.md (if structure changed)
- README.md (if user-facing behaviour changed)
